## What surprised me / patterns that emerged

- A deploy can be green from one entry point (manual `vercel --prod` run from the right subdirectory) while the project's actual configured entry point (Git-integration auto-deploy) is silently broken. "The site is live" and "the next push will deploy cleanly" are different claims; checking `git log origin/main..HEAD` and the GitHub check status caught the gap that a simple `curl` on the live URL would not have.
- The `vitest/globals` warning had been carried across two documentation files (`STATUS.md`, `HANDOFF.md`) as "non-blocking, clean up later" without anyone checking whether the codebase actually used the ambient types it referenced. It didn't. Worth a general habit: before deferring a recurring warning as harmless, check whether the thing it warns about is even in use — sometimes the fix is deletion, not investigation of the warning's root cause.

## Lessons learned

No new past-mistakes entry. Root-causing before patching (checking whether `vitest/globals` was actually used, rather than pinning a version or forcing a cache bust) is the existing systematic-debugging pattern working as intended, not a new lesson.
