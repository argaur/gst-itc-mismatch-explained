## 2026-08-24 — Parallel WebSearch-heavy agents exhaust the shared session quota fast
Launched 9-10 parallel primary-research agents, each expected to run 10-20 WebSearch calls. The session's WebSearch quota (default `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` = 200) is shared across the whole session, not per-agent, so it was exhausted partway through the fan-out — one agent (RTI primary) ran out of budget on its very first batch of queries and correctly refused to write a file rather than fabricate quotes, but had to be manually retried after raising the quota.
**Class of mistake:** planning a large parallel research fan-out without checking whether the session's default tool-call budgets (WebSearch, and likely others) can actually cover N agents x M calls each. Before launching a big parallel batch of search-heavy agents, either raise `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` in `.claude/settings.local.json` up front, or size the batch to the default 200-call ceiling.

## 2026-09-08 — Codex `--permission edit` is broken at a Windows sandbox layer deeper than `~/.codex/config.toml`
Dispatched Codex Sol (high effort) with `--permission edit --dir <worktree>` twice. Both times it refused every write and every shell command with `patch rejected: writing is blocked by read-only sandbox; rejected by user approval settings` and `CreateProcess ... blocked by policy`, confirmed independently via `git status`/`git diff --stat` showing zero changes (not just trusting Codex's own report). Root-caused to `~/.codex/config.toml`'s `[windows] sandbox = "unelevated"` line; removed it, retried, still blocked — and the second failure was worse, rejecting even read-only introspection commands (`rg --files`, `Get-Location`) "before process start." That escalation (a different, stronger failure mode after the "fix") was the signal the real block sits at a deeper sandbox/policy layer than that config file, not that the fix needed a third variation. About 700,000 tokens were burned across the two failed attempts before switching approach: run Codex read-only (its always-working path) to have it design complete literal file content, then have Claude place every file mechanically and run verification itself.
**Class of mistake:** not really a mistake in the moment (each attempt was reported plainly rather than silently retried), but worth recording as a known environment defect rather than re-discovering it: on this machine, Codex's `edit` permission path via `codex-delegate.sh` cannot currently write files or spawn subprocesses on Windows, regardless of `-s workspace-write`/`--dir` flags, and a `config.toml` edit alone does not fix it. Before spending another edit-permission attempt on this machine, default to the read-only-design + Claude-places-files pattern instead, and treat `--permission edit` as untrusted here until someone fixes the underlying sandbox/policy layer and verifies a real write succeeds.
