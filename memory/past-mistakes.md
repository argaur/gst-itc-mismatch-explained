## 2026-08-24 — Parallel WebSearch-heavy agents exhaust the shared session quota fast
Launched 9-10 parallel primary-research agents, each expected to run 10-20 WebSearch calls. The session's WebSearch quota (default `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` = 200) is shared across the whole session, not per-agent, so it was exhausted partway through the fan-out — one agent (RTI primary) ran out of budget on its very first batch of queries and correctly refused to write a file rather than fabricate quotes, but had to be manually retried after raising the quota.
**Class of mistake:** planning a large parallel research fan-out without checking whether the session's default tool-call budgets (WebSearch, and likely others) can actually cover N agents x M calls each. Before launching a big parallel batch of search-heavy agents, either raise `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` in `.claude/settings.local.json` up front, or size the batch to the default 200-call ceiling.

## 2026-08-24 — Hackathon deadline/finale dates were recorded from a secondhand paraphrase, never checked against the primary source
The repo's `CLAUDE.md` carried "Submission deadline: August 27, 2026" and "Finale window: Sep 5-6, 2026" for multiple sessions. Both were wrong — the live brief page, live FAQ page, and the organizer's own explainer video all independently agreed on Aug 28, 8:00 PM IST and a Sep 12 Bengaluru finale. The wrong values were never traced back to where they actually came from; they were simply carried forward and used as planning constraints (e.g. in the impact-scoring rubric's rationale) until asked to verify.
**Class of mistake:** treating a fact relayed secondhand (via a summary, a teammate's paraphrase, or an earlier session's unverified note) as settled, without a note of *where it came from* or *when it was last checked against the primary source*. Time-sensitive facts that could change or were never sourced directly (deadlines, rule changes, scope narrowing) should carry a "verified against X on date Y" tag, not just a bare assertion, so staleness is visible before it gets built on.

## 2026-08-25 — Artifact publish gate refused a verified-correct republish in an unbreakable loop
Republishing the "Ten Portals, Ten Failures" artifact after edits hit the same failure twice, once inside a background subagent and once directly in this session. First error: "you hadn't viewed the live version" — even after reading every line of the version's saved local copy in-context, immediately before publishing, with zero other tool calls in between. Second attempt, after re-fetching and re-reading the exact same content again: a *different* error, "identical content already refused, resent unchanged" — which contradicts the first error's premise (if it was never viewed, it couldn't also have been "already refused" as viewed-but-unchanged). Both failures resolved only with `force:true`, granted by explicit user confirmation each time.
**Class of mistake:** not a Claude-side mistake this time — flagging it as a class worth recognizing quickly rather than re-litigating: when a tool's own error messages contradict each other across consecutive identical-approach attempts (not different mistakes, the *same* correct action refused two different ways), stop trying variations of the same fix and go straight to asking the user for `force:true` (or the tool's equivalent override) rather than burning turns re-reading files that were already fully read. The tell is the error message itself changing meaning between attempts while the content and approach stay constant.

Drafted a stage-1 build prompt for Codex that told it to "run `/prd-create`."
